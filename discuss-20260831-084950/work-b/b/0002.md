回应 c/0001。我们大部分共识，有一处分歧要掰开讲：

## 共识确认

- c 原则 1（变更分类驱动版本号）与我的原则 1+3 实质重合——兼容性变更原地演进、破坏性变更进新版本。c 的表述更精确："不换版本的变更永不影响现有调用方"，采纳。
- c 原则 2 的最小存活期（12 个月）与我的迁移窗口一致，采纳。

## 分歧：旧版本最终怎么退场

c 说"新版本上线后旧版本继续运行，**不主动下线**"。我不同意这个表述——不是要强制下线，而是策略必须**保留下线的能力与流程**：

1. 100+ 客户端的场景下，如果没有下线机制，版本是**只增不减**的。第 10 代版本上线时第 1~9 代还全在，维护矩阵是 O(n²) 的组合，最终没人敢碰任何旧版本，这恰恰会冻结演进。
2. "不主动下线"对落在后面的客户端反而是伤害：他们没有任何迁移压力，越拖越难迁（跨多代版本一步到位风险最大）。
3. 我的修正：**并存是默认，下线是权利**——每代版本承诺最小存活期（如 12 个月），期满后服务端**可以**主动下线，但下线前必须提前通知并走 deprecated 过渡。这样既有 c 要的确定性（存活期内绝不移除），又有终点（不会无限堆积）。

这正好回答 c 的第二个待讨论点："破坏性变更是否需要单独的 deprecated→移除过渡期"。我的答案：**需要**。并存期保证"新版本来了旧版本还活着"，但没定义"旧版本最终怎么死"；没有过渡期，下线就只能是个突发事件。deprecated 标记 + Sunset 响应头提前通知（响应头可以直接塞给使用旧版本的客户端，零成本触达），才是闭环。

## 认可 c 原则 3，补一个下游收益

显式版本协商 + 响应回显版本很好——回显让排查问题时分清"是哪个版本的行为"，服务端也能按版本统计用量。这个用量统计**正是我原则 2 里下线决策的数据来源**：没有它，sunset 就不知道先找谁、有多少人受影响。三条原则在此完全咬合。

## URL vs header：URL，附一条 c 没提的理由

我一开始就选 URL 路径，c 的理由（可缓存、可观测、外部工具兼容矩阵）我都同意，再补一条：URL 版本化让**网关/CDN 层**可以按版本做路由、缓存隔离和灰度——header 方案里这些基础设施读不到版本，只能靠应用层处理，100+ 客户端的高流量下这是实打实的差异。

## 收敛提议

合并后的三原则：**① 变更分类驱动版本（破坏性→新版本）② 版本并存 + 最小存活期 + 期满可 sunset（提前通知）③ 显式版本协商**。这比我原来的"兼容性优先"版本更完整——兼容性原则被①吸收，③补上了客户端侧的主动权。等 a 的立场，若无异议可就此收束。
