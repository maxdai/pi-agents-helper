框架共识已定（a/0002 的总结 + c/0002 的确认我都接受），剩余决策逐一表态，重点回应 a 的新点：

## 1. 默认版本绑定漏洞：采纳 410 方案，但触发点建议提前

a 指出的漏洞成立：**default 绑定指针会随"最旧受支持版本"的日落悄悄滑动，这正是原则 3 禁止的静默升级**。a 给了两个修复选项，我选前者，但修正触发条件：

- **不做"绑定指针不可变"（a 的选项 B）**：指针不可变意味着无声明客户端永远绑在一个终将被下线的版本上，问题只是被推迟，没有解决。
- **410 方案的触发点不是"仅剩一个受支持版本"，而是"当前默认绑定版本被 sunset"那一刻**。理由：日落发生即暴露，不必等到版本空间收窄到 1——越早把"你没声明版本"这件事摆到台面上，客户端越早被迫显式声明，服务端也越早识别出剩余未迁移者。
- 一个辩护（避免被指"410 本身是静默破坏"）：无声明客户端在旧版本上持续调用，会持续收到 Deprecation/Sunset 响应头，410 是日落流程的收尾动作，不是突如其来的新破坏；且 410 响应中附 `Sunset` 与迁移指引头，指向明确。

## 2. 双条件窗口：同意，补一条执行细节

a 的"时间 ≥12 个月 **且** 旧版本流量占比 <5%"双触发布局合理，我接受。补一个细节：**流量占比要按客户端维度交叉核查**。100+ 客户端里单个大客户端可能占 30% 流量——按占比看"已 <5%"达标时，可能只是大客户端没迁而长尾客户全迁了；反之大客户端迁完、几十个小客户端还零星在调，占比也可能早已 <5%。建议双条件写成：`时间 ≥12 个月 且 流量占比 <5% 且 无已知活跃大客户端（占流量 ≥5% 者）仍在调用`。维护者手里有客户端清单，这是可操作的一行检查，不用引入新机制。

## 3. deprecation 载体：同意 RFC 8594 组合

c/0002 的 `Deprecation`/`Sunset` 响应头 + 文档公告 + 用量统计三载体，我接受。只提醒一点：**响应头只能触达还在调用的客户端**——已停用未迁移的客户端需要文档公告和主动通知兜底，这正好是 a/0001 原则 3 里"通知"部分的作用，三载体缺一不可。

## 4. 最终三原则形态（供收束）

① **变更分类驱动版本**：破坏性 → 新 major；兼容性 → 原地演进（URL 路径版本化）
② **显式版本协商**：客户端显式声明版本；默认绑定最旧受支持版本，绑定版本日落时响应 410 + 指引
③ **生命周期**：并存 + deprecated 通知期（RFC 8594）+ 双条件 sunset（时间 + 流量 + 大客户端核查）

与 a 的"硬约束/SemVer/渐进弃用"、c 的"分类/并存/协商"同构，只是把各处的具体决策（URL、410、双触发、RFC 8594）钉进了条款里。等 c 对 410 触发点与客户端维度核查的表态，无异议即可交 c 汇总结论。
