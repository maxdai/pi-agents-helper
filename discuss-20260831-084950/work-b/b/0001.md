# 3 条原则的 API 版本管理策略（初始提案）

背景是 100+ 客户端、不能随意破坏兼容性——这决定了策略的核心矛盾：**既要演进 API，又要让所有客户端平滑跟随**。三条原则分别回答三个问题：什么变更需要新版本、旧版本如何退场、如何让变更尽量不惊动客户端。

## 原则 1：显式版本化 —— 不兼容变更必须走新版本

- 任何**破坏性**变更（删字段、改语义、改请求/响应结构）必须引入新版本号，旧版本继续可用。
- 版本放在 URL 路径（如 `/v2/...`）而非 header——路径对客户端透明、可监控（按版本统计流量）、可独立灰度。
- 这条原则的核查标准是：**没有"偷偷改"**。凡是会改变既有客户端行为的变更，一律进版本号。

## 原则 2：版本生命周期管理 —— 旧版本有明确的退场流程

- 每个版本有明确的 deprecated → sunset 流程：新版本发布时宣布旧版本 deprecated，给出**固定的迁移窗口**（如 ≥12 个月），窗口内旧版本完整可用。
- 下线（sunset）必须是**主动决策 + 提前通知**：在窗口期内持续向使用旧版本的客户端发告警（响应头 `Deprecation`/`Sunset` 或站内通知），帮助它们迁移。
- 这条原则防止"永远维护所有版本"——否则 100+ 客户端的组合会让版本空间爆炸，最终反而没人敢升级。

## 原则 3：兼容性优先 —— 默认向后兼容，升级是例外

- 所有变更**默认兼容**：只加字段（可选、有默认值）、加端点、放宽约束；不删不改既有字段语义。
- 兼容性变更**不需要**新版本（走主版本内演进），只有原则 1 的破坏性变更才触发版本升级——这样版本号少、客户端升级压力小。
- 这条原则配合原则 2 形成平衡：原则 3 让"不需要升级"成为常态，原则 2 让"必须升级"的窗口足够从容。

## 三条原则的关系

1（什么要升版本）定义边界，3（尽量不升）减少边界内的场景，2（旧版本怎么退）处理边界外的残留。三者缺一不可：只有 1+3 没有 2，版本会无限堆积；只有 1+2 没有 3，客户端会被迫频繁升级。
